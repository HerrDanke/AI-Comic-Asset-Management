| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | ⭐⭐ | 双 Store 同步是最大隐患，数据一致性靠人工维护 |

## 二、优化计划（按优先级排序）

### 🔴 P0 — 架构修复（必须做，消除隐患）

#### 0.1 合并双 Store 架构

| 项目 | 内容 |
|------|------|
| **问题** | `characterStore.character` 与 `projectStore.characters[]` 各存一份角色数据，通过 `syncToProjectStore` / `syncFromStore` 手动同步，极易不一致 |
| **影响** | 数据丢失、状态不同步、难以维护 |
| **方案** | 以 `characterStore` 为角色数据唯一 Source of Truth，`projectStore` 仅保留 `characterIds` 引用列表 |
| **改动范围** | `characterStore.ts`、`projectStore.ts`、`App.tsx` |
| **工作量** | 2-3 天 |
| **风险** | 需全面测试保存/加载/导入/导出流程 |

#### 0.2 版本快照改为 Diff 存储

| 项目 | 内容 |
|------|------|
| **问题** | `VersionSnapshot` 完整复制角色所有字段（含 traits、images），50 个版本 = 50 倍数据量 |
| **影响** | JSON 文件膨胀、加载变慢、保存延迟 |
| **方案** | 存储变更字段 diff（`{ field, oldValue, newValue }`），渲染时从 base + diffs 重建 |
| **改动范围** | `types/index.ts`、`characterStore.ts`、`VersionHistory.tsx`、`commands.rs` |
| **工作量** | 3-4 天 |
| **风险** | 需兼容旧版 full snapshot 数据（自动迁移） |

#### 0.3 列表接口懒加载

| 项目 | 内容 |
|------|------|
| **问题** | `listCharacters` 返回完整 `CharacterData[]`（含 versions 数组），角色越多越慢 |
| **影响** | 首次加载卡顿、内存占用高 |
| **方案** | 新增 `listCharacterSummaries` 接口，仅返回 `{ id, name, role, color, updatedAt }`，详情按需 `getCharacter` |
| **改动范围** | `commands.rs`、`tauri.ts`、`projectStore.ts`、`CharacterList.tsx` |
| **工作量** | 1-2 天 |

### 🟠 P1 — 性能优化（显著提升体验）

#### 1.1 图片系统重构

| 项目 | 内容 |
|------|------|
| **问题** | 无缩略图、无缓存、每次 `getImageData` 重新 base64 编码 |
| **影响** | 大图加载慢、重复计算、内存浪费 |
| **方案** | ① Rust 端生成 256px 缩略图并缓存 ② 前端 LRU 缓存已加载图片 ③ 大图延迟加载（IntersectionObserver） |
| **改动范围** | `commands.rs`（新增 `get_thumbnail_data`）、`ImageGallery.tsx`、新增 `imageCache.ts` |
| **工作量** | 2-3 天 |

#### 1.2 写入队列按资源分队列

| 项目 | 内容 |
|------|------|
| **问题** | `tauri.ts` 中全局单一 `writeQueue`，所有项目/角色的写入操作互相阻塞 |
| **影响** | 切换项目时排队等待、保存延迟 |
| **方案** | 按 `{projectId}:{characterId}` 分桶队列，不同资源并行、同资源串行 |
| **改动范围** | `tauri.ts` |
| **工作量** | 0.5 天 |

#### 1.3 文本输入防抖

| 项目 | 内容 |
|------|------|
| **问题** | `updateField` 每次按键设 `isDirty: true`，30 秒定时保存时可能触发不必要的写盘 |
| **影响** | 频繁写盘、版本快照冗余 |
| **方案** | 对 `updateField` 做 500ms debounce 后才标记 dirty |
| **改动范围** | `characterStore.ts` |
| **工作量** | 0.5 天 |

#### 1.4 自动保存策略优化

| 项目 | 内容 |
|------|------|
| **问题** | 30 秒定时 + 失焦保存，无用户可控选项 |
| **影响** | 部分用户希望更频繁保存，部分希望减少写盘次数 |
| **方案** | 新增设置面板：保存间隔可调（10s/30s/60s/手动）、开关失焦保存 |
| **改动范围** | `App.tsx`、`Topbar.tsx`、新增 `settingsStore.ts` |
| **工作量** | 1 天 |

### 🟡 P2 — 安全与健壮性

#### 2.1 Rust 端错误处理规范化

| 项目 | 内容 |
|------|------|
| **问题** | `get_app_data_dir()` 使用 `expect()`，异常时直接 panic 崩溃 |
| **影响** | 用户主目录不可用时应用闪退 |
| **方案** | 全部改为 `Result<T, String>`，前端做降级提示 |
| **改动范围** | `commands.rs`（约 15 处 `expect`） |
| **工作量** | 1 天 |

#### 2.2 路径遍历防护

| 项目 | 内容 |
|------|------|
| **问题** | `get_image_data` / `delete_image` 直接拼接 `image_name`，未验证是否在预期目录内 |
| **影响** | 恶意构造 `../../etc/passwd` 可读取任意文件 |
| **方案** | 使用 `Path::canonicalize()` + `starts_with(images_dir)` 验证 |
| **改动范围** | `commands.rs` |
| **工作量** | 0.5 天 |

#### 2.3 文件上传校验

| 项目 | 内容 |
|------|------|
| **问题** | 前端有 extensions 过滤，但 Rust 端无大小/MIME 校验 |
| **影响** | 可上传超大文件或伪装扩展名的恶意文件 |
| **方案** | Rust 端限制单文件 ≤10MB、校验 MIME 类型与扩展名一致 |
| **改动范围** | `commands.rs`（`save_image`） |
| **工作量** | 0.5 天 |

#### 2.4 导入数据 Schema 校验

| 项目 | 内容 |
|------|------|
| **问题** | `import_project` 直接 `serde_json::from_str`，无结构校验 |
| **影响** | 损坏/篡改的 JSON 可能导致 panic 或数据污染 |
| **方案** | 使用 `jsonschema` crate 校验导入文件结构，拒绝非法数据 |
| **改动范围** | `commands.rs`、`Cargo.toml` |
| **工作量** | 1 天 |

## 四、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 双 Store 合并导致数据丢失 | 中 | 高 | 合并前自动备份 `~/AIComicCharacterDB/` |
| Diff 快照渲染性能差 | 低 | 中 | 限制最大 diff 链长度（如 100），超过则存 full snapshot |
| 缩略图生成占用磁盘 | 中 | 低 | 缩略图目录可清理、限制总大小 |
| 旧版数据不兼容 | 中 | 高 | 保留导入时的版本检测 + 自动迁移 |

## 五、验收标准

- [ ] 双 Store 合并后，所有保存/加载/导入/导出场景数据一致
- [ ] 100 个角色项目加载时间 < 500ms
- [ ] 50 个版本的角色保存时间 < 100ms
- [ ] 上传 20MB 文件被拒绝、路径遍历被拦截
- [ ] Ctrl+Z 可撤销最近 20 步操作
- [ ] 核心 store 操作测试覆盖率 > 80%
- [ ] 无 `expect()` / `unwrap()` 残留在生产代码路径
